## Operating model

**One stage per session.** Do not attempt several stages in one run. Each stage is a self-contained task whose state lives in files, not in your context. This is what makes the pipeline survivable across sessions, timeouts, and interruptions.

### Resume protocol

At the start of every session, determine where the project stands **from the filesystem**, never from assumption:

1. Read every file in `results/gates/`.
2. Read `RUN_REPORT.md` if it exists.
3. Read `experiments/LEDGER.md` for runs that started but never ended.
4. Identify the highest stage whose gate has PASSed. That stage is done; the next one is your task.

If a gate is missing but its stage's outputs exist, the stage was interrupted. Finish it and write the gate — do not redo it from scratch, and do not skip it.

### Long-running jobs

**Never run training in the foreground of an agent session.** Sessions end; training does not care.

- Launch every training run **detached**, writing to `experiments/<run_id>/logs/`.
- Record the process/job id in `experiments/<run_id>/job.json` along with the launch command.
- Append the START line to the ledger at launch, not at completion.
- On resume, check `job.json` for every run without an END line. If the job is still alive, wait or report; **do not relaunch it**. If it died, record `status=crashed` with the last log lines.

A run that outlives the session is normal and expected. A run relaunched on top of itself corrupts the ledger and wastes the compute.

## Gate protocol

A gate is a check that **reality can fail**. Every gate writes one file:

`results/gates/G<N>_<name>.json`

```json
{
  "gate": "G3_baseline",
  "stage": "03_data",
  "timestamp": "2026-09-03T14:05:00",
  "check": "what was measured, in one sentence",
  "reference_value": null,
  "reference_source": "where the expected value comes from",
  "observed_value": null,
  "tolerance": "the threshold, declared BEFORE measuring",
  "verdict": "PASS | FAIL",
  "evidence": ["relative/paths/to/files/that/prove/this"],
  "notes": "anything the user needs to know"
}
```

Rules:

- Declare `tolerance` **before** producing `observed_value`.
- Never edit a gate file after writing it. A re-run creates `G<N>_<name>_rerun<K>.json` and must state why.
- `verdict: FAIL` is a legitimate, expected outcome. It is **not** a failure of your work. Reporting a FAIL honestly is worth more than a PASS you had to arrange.

## Scientific integrity

**Never fabricate, invent, or synthesize experimental results.**

Every number, table, figure, metric, and claim in the manuscript must derive from real data, real checkpoints, and real model predictions produced by this project.

`01_integrity.md` defines the enforcement: the provenance record every result file must carry, the append-only run ledger, the forbidden operations, and `scripts/audit.py`.

Two outcomes are always acceptable and must never be avoided by inventing something:

- **Negative result** — the method did not work. Written up as such (`07_paper.md`).
- **INCOMPLETE** — a result could not be produced. Reported as a gap (`01_integrity.md` § The Honest Exit).

A fabricated positive result is worse than either. If evidence is insufficient, say so explicitly.

The run ends when one of these is true:

- `08_review.md` emits `READY_FOR_SUBMISSION`.
- `08_review.md` emits `NOT_READY_FOR_SUBMISSION` with the blocking reasons.
- Any gate FAILs.
- An iteration budget is exhausted (3 in stage 3, 3 in stage 7).
- A required result cannot be produced, and the run is reported `INCOMPLETE`.
